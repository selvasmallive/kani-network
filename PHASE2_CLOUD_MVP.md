# KANI Phase 2 Cloud MVP

Status: started
Scope: `phase2-lean-no-gke` sandbox cloud deployment path

## Objective

Phase 2 moves the Phase 1 local MVP into a minimal Google Cloud sandbox while keeping cost and operational complexity low:

- `kani-api` runs on Cloud Run.
- Validator finality runs as a Cloud Run Job.
- Cloud Scheduler runs the validator job on a low-frequency sandbox cadence.
- PostgreSQL ledger state runs on Cloud SQL.
- Container images are built into Artifact Registry.
- `DATABASE_URL` and sandbox API keys are generated by Terraform and stored in Secret Manager.
- Basic sandbox compliance screening gates JSON and ISO payment submission before transactions are queued.
- Basic ISO 20022 `pacs.008` ingestion maps one sandbox credit transfer into the ledger payment flow, `pacs.002` reports the resulting payment status, and `camt.053` returns account statements from finalized journal entries.
- A project-scoped Cloud Billing budget alert is created as a cost guardrail.
- Pub/Sub and `kani-cost-guard` are provisioned for programmatic budget notifications, and the Cloud Billing budget is attached to the Pub/Sub topic.
- Cloud Monitoring alert policies watch API errors, validator job errors, Scheduler errors, Cloud SQL errors, and budget-brake activity.

This phase still does not move real value.

## Lean No-GKE Topology

```text
Institution / operator
        |
        | Cloud Run IAM + sandbox institution headers
        | API keys loaded from Secret Manager
        v
Cloud Run service: kani-api
        |
        | DATABASE_URL from Secret Manager
        v
Cloud SQL PostgreSQL
        ^
        |
Cloud Run job: kani-sandbox-validator
        ^
        |
Cloud Scheduler: kani-sandbox-validator-schedule
        ^
        | pause when budget brake triggers
Cloud Run service: kani-sandbox-cost-guard
        ^
        |
Pub/Sub topic: kani-sandbox-budget-notifications
        ^
        | Cloud Billing budget attachment, if domain policy allows it
Cloud Billing budget: kani-sandbox-monthly-budget
        |
        v
Cloud Monitoring alerts: API / validator / Scheduler / SQL / budget brake
```

The validator job runs `kani-node` in `sweep` mode. One job execution walks the Phase 1 sandbox validator identities:

```text
validator-a, validator-b, validator-c
```

This preserves the Phase 1 PoA/finality model for MVP testing without paying for a GKE cluster or node. It is not a production validator network and does not provide validator host isolation.

## Minimum Required Resources

Terraform now plans only the minimum resources needed for the end-to-end cloud MVP:

- Required Google APIs: Artifact Registry, Billing Budgets, Cloud Build, Cloud Resource Manager, Cloud Scheduler, IAM, Cloud Monitoring, Cloud Run, Pub/Sub, Secret Manager, Cloud SQL Admin.
- Artifact Registry Docker repository: stores the shared `kani-api` / `kani-node` image tagged as `latest` and by Cloud Build ID.
- Cloud SQL PostgreSQL instance: Enterprise edition, `db-g1-small`, `10 GB` HDD, zonal, automated backups enabled, PITR enabled.
- Secret Manager secrets: store the generated Cloud SQL socket `DATABASE_URL` and generated sandbox API keys.
- Cloud Run service: `kani-sandbox-api`, scale-to-zero, max `1` instance.
- Cloud Run job: `kani-sandbox-validator`, one task, `sweep` mode, max `25` transactions per block.
- Cloud Scheduler job: `kani-sandbox-validator-schedule`, every `15` minutes, OAuth-authenticated to the Cloud Run Jobs API.
- Cloud Monitoring email notification channel: explicit budget alert recipient for `selva@kani.network`.
- Cloud Billing budget: project-scoped monthly budget alert, default `50` units in the billing account currency, with alerts at `50%`, `80%`, and `100%`.
- Cloud Monitoring alert policies: log-match alerts for API 5xx/error logs, validator job error logs, Scheduler error logs, Cloud SQL error logs, and cost-guard budget-brake warnings/errors.
- Pub/Sub topic and push subscription: receives budget status messages and pushes them to the cost guard service.
- Cloud Run cost guard: `kani-sandbox-cost-guard`, scale-to-zero, pauses the validator Scheduler job when actual spend crosses `80%` of budget.
- IAM service accounts and minimum runtime permissions for Cloud SQL and Secret Manager.
- Cloud Build runtime IAM grants for source archive reads, Artifact Registry writes, and build logging.

Skipped for this profile:

- GKE cluster and node pool.
- Compute Engine node costs.
- VPC/subnet created only for GKE.
- Cloud Storage block archive bucket.
- Cloud KMS key ring/key.
- Cloud Armor, API Gateway, mTLS, HSM, and production monitoring.

Bring GKE back later when you are ready to test real validator operations, host isolation, node upgrades, and multi-zone behavior.

## Cost Controls

The default Terraform variables are tuned for a free-trial sandbox:

- `deletion_protection = false` so you can destroy resources after testing.
- `cloud_run_max_instances = 1`.
- `cloud_run_ingress = "INGRESS_TRAFFIC_ALL"` so direct Cloud Run testing works without a load balancer; Cloud Run IAM still controls invocation unless you explicitly grant public access.
- `database_tier = "db-g1-small"`.
- `cloud_sql_disk_size_gb = 10`.
- `cloud_sql_disk_type = "PD_HDD"`.
- `cloud_sql_backups_enabled = true`.
- `cloud_sql_point_in_time_recovery_enabled = true`.
- `cloud_sql_backup_start_time = "07:00"` for a UTC backup window.
- `cloud_sql_backup_retained_count = 7`.
- `cloud_sql_transaction_log_retention_days = 7`.
- `KANI_REQUIRE_CONFIGURED_SANDBOX_API_KEYS = TRUE` in Cloud Run so the cloud API fails startup if Secret Manager keys are not injected.
- `validator_schedule = "*/15 * * * *"` so the validator job is not running constantly.
- `budget_amount_units = 50` with alert thresholds at `0.5`, `0.8`, and `1.0`.
- `budget_alert_emails = ["selva@kani.network"]` links an explicit Cloud Monitoring email notification channel to the budget.
- `budget_pubsub_topic_attachment_enabled = true` normally attaches the Cloud Billing budget to Pub/Sub. Set it to `false` if domain-restricted sharing blocks the Google-managed publisher, then have an org-policy admin do the temporary exception and attachment later.
- `budget_brake_threshold = 0.8` pauses `kani-sandbox-validator-schedule` when programmatic budget notifications show actual spend crossing `80%`.
- `budget_brake_dry_run = false` means the pause action is active.
- `monitoring_alerts_enabled = true`.
- `monitoring_alert_log_notification_rate_limit = "900s"` limits repeated log-match notifications.

Do not run `terraform apply` until you are ready to create paid sandbox resources.

Cloud Billing budgets are alerts, not hard caps. They help catch spend early, but they do not automatically stop resources.
The current sandbox billing account reports currency `CAD`, so the live guardrail is a `50 CAD` monthly alert budget.
Google may send a verification email for the Cloud Monitoring notification channel. Budget emails might not deliver to that explicit channel until the recipient verifies it.
The `kani.network` organization enforces legacy domain-restricted sharing. The initial budget-to-topic attachment required a temporary project-level override so Google could grant `billing-budget-alert@system.gserviceaccount.com` Pub/Sub Publisher on the budget notification topic; the override should remain reset after attachment.
The automated brake only pauses the validator Scheduler job. It does not stop Cloud SQL, Cloud Run API traffic, Artifact Registry storage, or all possible Google Cloud charges.
Cloud SQL backups and PITR add backup and transaction-log storage cost, but they are now enabled because the ledger is stateful even in sandbox.
Monitoring alert policies reuse the explicit budget email notification channel when one is configured. Alert delivery to that email may require the Google Cloud Monitoring channel verification email to be accepted.

## Phase 2 Acceptance Criteria

- Container image builds in Cloud Build and is available in Artifact Registry.
- Cloud SQL ledger instance exists for sandbox use.
- Secret Manager contains the generated Cloud SQL `DATABASE_URL`.
- Cloud Run `kani-api` starts with sandbox runtime flags.
- Cloud Run validator job starts with sandbox runtime flags and `sweep` mode.
- Cloud Scheduler can execute the validator job through the Cloud Run Jobs API.
- Cloud Billing budget guardrail exists for the sandbox project.
- Pub/Sub budget notification resources exist; the Cloud Billing budget is connected to Pub/Sub when org policy allows the Google-managed publisher.
- Cost guard Cloud Run service can receive budget notification messages and pause the validator Scheduler job when the brake threshold is crossed.
- Cloud Monitoring alert policies exist for API, validator, Scheduler, Cloud SQL, and budget-brake signals.
- A sandbox mint is queued by the API and finalized by the validator job.
- A sandbox transfer is queued by the API and finalized by the validator job.
- A self-transfer is blocked by the sandbox compliance profile before it reaches the pending transaction queue.
- A single-transfer ISO 20022 `pacs.008` message is parsed, queued by the API, and finalized by the validator job.
- A `pacs.002` XML status report is returned for the finalized ISO payment.
- A `camt.053` XML account statement is returned for the finalized sandbox account journal.
- Balances and latest block are readable from the cloud API.
- Audit events are still persisted.

## Known Gaps

- This profile does not run independent always-on validators.
- mTLS, API Gateway, and Cloud Armor are not wired yet.
- Compliance screening is intentionally basic and sandbox-only; it is not a substitute for AML/KYC, sanctions screening, case management, or legal review.
- ISO 20022 support is limited to one sandbox `pacs.008` credit transfer per XML document, basic `pacs.002` payment status XML, and account-scoped `camt.053` statement XML.
- KMS/HSM signing is not integrated into transaction or validator signatures yet.
- Cloud Storage block/audit archive export is deferred.
- BFT consensus is not part of this phase.
